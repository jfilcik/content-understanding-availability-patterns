Specifics of this example

Ready to try real requests? Follow the deployment setup and live lab exercise. This repository implements this single-APIM stage; the fourth stage in the architecture guide remains conceptual. This page is always an offline simulation, not a live client.

From the stage-three demo to a real deployment
  1. Choose a dedicated test resource group and copy main.example.bicepparam to main.bicepparam. Set publisher details, two supported regions, model versions/SKUs and quota. Sweden Central and West Europe are defaults, not required locations.
  2. Follow the validation and deployment commands. The scripts configure both CU stacks, the same analyzers, managed identities, signed result URLs and persistent active-backend selection. Wait for both stacks' provisioning to finish.
  3. Start the local helper as shown in the app setup guide. It imports deployment outputs when Azure controls are enabled. In the app, obtain an APIM serving subscription key from the portal instructions, then deliberately submit one sample invoice. This creates real, potentially billable usage.
  4. Verify a primary baseline, a genuinely overdue pending or late-completed result, propagation to secondary for new work, and unchanged primary polling for the original job. Restore any test threshold and explicitly reset backend selection as separate actions.

For stage four, design and test resilient ingress separately: regional gateways, shared HTTPS configuration, cross-gateway validation of original operation affinity, meaningful probes and DNS failover behavior. The current single-gateway signing/binding policy cannot simply be copied twice unchanged.

Inside the gateway


          

        

        

        

          Open the synthetic signed-token envelope
          
Format: Base64(UTF-8 JSON).Base64(HMAC-SHA256(secret, encodedPayload)). The complete token is URL-escaped in gateway-token. This is not a JWT.

          

          
Synthetic token only: its signature is deliberately invalid. Never send it to APIM.

          Locally decoded example claims (not verified)
          

          
Signed, not encrypted. Anyone holding a URL can decode these claims. Only APIM, holding the signing secret, can validate the HMAC. The client must still send its APIM serving subscription key; the token is not a substitute.

          
APIM checks the signature and operation, allowed region, gateway, subscription, API version, APIM hostname and timestamp/lifetime bindings. The analyzer is included for correlation. The browser's decoded preview is not trusted routing evidence.

        

      

    

    

      

        
Three transformations, two directions

        
What APIM actually rewrites

        
    
          
  1. Analyze request, inbound: retain the Analyze route and API version; select the CU destination using active-backend. Remove client subscription credentials before forwarding and use APIM's managed identity for CU authentication.
    2. 
          
  2. Accepted response, outbound: replace CU's original Operation-Location hostname with APIM's hostname and API path, adding the signed routing token. The client receives an APIM result URL, not the native CU URL.
    3. 
          
  3. Result GET, inbound: validate the unchanged signed URL, choose the accepting backend from validated claims, strip gateway-token and client credentials, then forward the result request to CU. This is destination routing, not a second Operation-Location response rewrite.
    4. 
        

        

          Read a static before / after example
          CU accepted response (illustrated backend header)
          
Operation-Location: https://cu-primary.example.invalid/contentunderstanding/analyzerResults/op-A?api-version=2025-11-01

          APIM accepted response (client-facing header)
          
Operation-Location: https://gateway.example.invalid/contentunderstanding/analyzerResults/op-A?api-version=2025-11-01&gateway-token=<URL-escaped payload.signature>

          
Client GETs that complete returned URL unchanged, with its serving subscription key. APIM removes the token and forwards to the primary CU URL above, even after new submissions switch to secondary.

        

      

      

        
Observation, not a stopwatch

        
What requests secondary selection?

        

          Primary-degradation examples while primary is active; normal threshold = 60 seconds.
          
Observed eventSwitch request?

          
            
Primary GET: HTTP 200, Running / NotStarted, signed age > 60s (e.g. 61s)Yes, pending-latency path

            
Primary GET: HTTP 200, Succeeded, signed age > 60s (e.g. 61s)Yes, completion-latency path; the result is still returned

            
Primary GET: Running or Succeeded at exactly 60sNo; strictly greater is required

            
Primary GET: Failed / Canceled at any ageNo; terminal failures do not qualify

            
Result for an operation accepted by secondary, or any GET once secondary is activeNo; both accepting and active backend must be primary-cu

            
Primary POST: 429 / 5xx, or forward-request errorYes, submission-error path; original failure returned

            
Slow HTTP round trip, animation timer, missing Retry-After, or no pollingNo latency evidence

            
Restoring a temporary thresholdNo; it does not reset selection

          
        

        
Age starts at APIM's receipt of the original Analyze POST (the signed started time). It includes polling gaps and client pauses, not pure engine time, so a delayed successful poll can trigger even if the service finished earlier. Live CU pending responses omitted Retry-After; the policy does not use that header. There is no health endpoint or synthetic probe; the last real response headers show the runtime backend, and a management-plane acceptance is not runtime activation. A temporary 2s test threshold is not an HTTP timeout or a guaranteed two-second switch.

      

    

    

      
The boundaries worth remembering

      

        
InvariantWhy it matters

        
          
ARM acceptance is not runtime activationAPIM uses managed identity to read and ETag-conditionally update its own named value. Conflicts or management failures can prevent switching; accepted writes take time to propagate. A previous response alone does not prove a new Analyze will use secondary; there is no health probe, and the last real response headers show the runtime backend.

          
Existing work never movesOperation A stays in Sweden Central. A full primary outage can break its GETs even while new secondary jobs succeed. There is no automatic migration or replay of uncertain POSTs; resubmission can duplicate work and cost.

          
Secondary selection is stickyNo automatic failback or reverse failover. Restoring a threshold is separate from explicitly resetting active-backend to primary. Secondary health is not independently qualified by this switch.

          
One APIM remains one dependencyThis design addresses CU backend degradation, not an outage of the APIM region. Both regional analyzer/model stacks must be prepared before serving work; nothing is copied during failover.
