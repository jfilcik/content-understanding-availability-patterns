High availability and disaster recovery for Content Understanding

Work in progress (WIP). This guide and the example lab are under active development. Details may change or be incomplete. Use them for learning and experimentation, not as production-ready guidance.

Design a highly available Azure Content Understanding (CU) system by addressing each dependency separately. Start with regional job ownership, choose model and OCR processing scopes, then add CU regional failover and resilient ingress.

Understand the service boundaries

A job belongs to a regional CU resource

The CU resource that accepts an Analyze request tracks that job and serves its results. Customer data at rest stays in the same region as the CU resource. Input documents, intermediate representations and final results are retained for up to 24 hours, then automatically deleted; Delete Result can remove them earlier. Choose that region to meet your storage requirements, and retain completed results in your application's durable store.

Processing services have their own scope

CU uses OCR/layout processing and your configured language models, including Azure OpenAI models in Microsoft Foundry, to extract fields. Model deployment type and supported OCR processingLocation settings independently determine where processing can occur. Data Zone or Global processing can use capacity beyond one region; it does not relocate the CU job or its stored results.

Separate storage location from processing location. A regional endpoint alone does not guarantee all processing stays in that region. Operation-Location is the response header containing a job's polling URL, not a model or OCR location setting.

    Processing scope and configuration reference

    Model inference uses a deployment type, not Operation-Location or the CU resource's Azure location. Data Zone Standard (DataZoneStandard) and Global Standard (GlobalStandard) dynamically route to eligible datacenters within their respective boundaries. Geography-based types do not guarantee processing exclusively in one region. Broader capacity does not guarantee recovery from loss of the model endpoint's primary region.

    OCR/layout has a different control: processingLocation, with values geography, dataZone and global. Public CU guidance scopes it to prebuilt-read and prebuilt-layout. Step 3 carries forward step 2's model configuration to show the independent controls; an OCR-only request does not need an LLM call.

    The sample defaults model deployments to GlobalStandard and does not automatically broaden OCR scope. Check current model, analyzer, API and region support: Foundry model deployment types, CU data handling and processing locations, and Traffic Manager DNS routing.

    Implement regional CU failover

    The sample implements step 4: one APIM gateway, two prepared CU resources and signed result URLs that keep each job with its accepting region. Follow normal operations, primary degradation and failover in the single-APIM walkthrough, then deploy the lab.

    Deploy and validate

    1. Follow Azure deployment setup: sign in, choose a dedicated test resource group, copy the parameter file and select two supported regions/models before deploying.
    2. Run validation and deployment with the provided scripts. They provision the same analyzers in both CU resources and preserve the gateway's signing/serving credentials on redeployment.
    3. Start CU Observatory locally, add the APIM serving key and submit a sample invoice. Inspect the real POST/result traffic, then use the bounded failover and recovery exercise.

    Azure resources and analyses incur charges. Sweden Central and West Europe are defaults; choose supported regions, model deployments and capacity before deploying.

    Plan recovery beyond routing

    Set recovery time (RTO) and recovery point (RPO) objectives for your application. Keep source documents and completed results in application-owned durable storage; CU's up-to-24-hour retention is not a backup. Securely track the accepting resource and polling URL for every job, and prepare matching analyzers, model mappings, permissions and capacity in secondary before an incident.

    A regional outage can leave previously accepted results unavailable. Define deliberate resubmission and duplicate-reconciliation rules, then test failover and explicit failback. This sample never automatically replays submissions or migrates jobs. Review the recovery checklist and implementation limits.
